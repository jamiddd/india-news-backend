# Open sourcing, and what it does (and does not) prove

Decision recorded 5 September 2026. **Target: open up around November–December
2026**, deliberately not before — the Play release and the donations launch
come first, and both are easier to run without a public repo attached.

The motivation is trust: making it verifiable that the media-framing output is
not editorially slanted. That goal is right. The mechanism needs adjusting,
because publishing the source code does not, by itself, establish it.

---

## The gap in "open source, therefore unbiased"

Framing text is generated by an LLM reading publisher content. The code that
would become public describes *how the model is called*; it says nothing about
whether the output leans. Nor can a reader reproduce our outputs to check:
same prompt and same articles on a different day, with a different model
version, produce different text.

So a sceptical reader gets no evidence from the repository alone, and a claim
of "unbiased because open source" is likely to cost more credibility than
staying quiet would. What follows is what actually carries the claim.

## What actually supports the claim, best value first

1. **Publish the prompt, verbatim and versioned.** The prompt *is* the
   editorial policy. A prompt that says "describe the angle each outlet led
   with, neutrally, without evaluating which is correct" is a commitment
   somebody can hold us to. This is one file and it does most of the work —
   opening everything *except* the prompt would be theatre.

2. **Make each framing row provable inside the app.** Put the source article
   one tap from the framing line describing it. A reader who can check "did Al
   Jazeera actually lead on that?" against the original does not have to trust
   us at all. Articles already link back to publishers, so this extends
   something that exists.

3. **Publish the source list and the basis for it.** Probably the largest real
   bias vector, and easy to underrate next to the wording of any single
   framing sentence: *which outlets are ingested* shapes the spread of angles
   far more. A reader who distrusts us looks here first.
   `scripts/seed_sources.py` and the add/remove scripts make the decision
   auditable.

4. **Publish the eval harness and its results over time.** An eval harness
   already exists for clustering. Framing quality measured in public is
   evidence in a way source code is not.

## Scope: not the whole backend

Recommended: open the enrichment pipeline, the prompts, the source list and
the eval harness — the parts the claim rests on. Auth, donations and
notification plumbing prove nothing about neutrality, and every extra file is
more surface to review for secrets and more support burden for one person.

A smaller repo focused on exactly what a sceptic wants to read is *more*
persuasive than a full dump, not less.

## Go in with eyes open

- `scripts/purge_fabricated_framing.py` and
  `scripts/clear_rulebased_framing.py` exist because the system has produced
  framing that had to be deleted. Every honest pipeline has such a history,
  but an outside reader may find these and draw conclusions. Far better to
  describe what happened, and what detects it now, than to let it be
  discovered.
- A public repo brings issues, PRs and support requests to a solo developer.
- It makes the ingestion pipeline and source list visible to publishers, some
  of whom take a dim view of aggregation.

## Before flipping it public

- Run a real secret scanner over the **full history**, not just the working
  tree: `gitleaks detect --no-git=false`, or
  `trufflehog git file://.`. A heuristic scan on 5 September 2026 found
  nothing — no `.env` (only the tracked `.env.example`), no
  `*firebase-adminsdk*.json`, no Razorpay or Anthropic key-shaped strings, and
  the one commit mentioning AWS credentials only renames variables — but that
  is not a substitute.
- Decide the licence.
- Add a README that states plainly what the framing pipeline does, what it
  cannot promise, and how to check it. This is the document that carries the
  trust claim; the code is supporting material.

## Cheap things worth doing in the meantime

None of these require the repo to be public, and all of them make opening it
later a smaller job:

- Keep prompts in one versioned file rather than inline string literals, so
  "publish the prompt" is a link and not an archaeology exercise.
- Keep prompt changes in their own commits with a note on the intent, so the
  editorial history reads clearly to an outsider.
- Write code comments as though a stranger will read them — this is already
  the house style, and it is the main thing that makes a repo openable on
  short notice.
